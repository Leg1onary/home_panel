# Расширяемая модель устройств v1

Home Panel 1.1.0 добавляет логические устройства поверх прежнего каталога каналов.
Это первый этап архитектуры, не редизайн и не универсальное управление всем HA.

## Три независимых слоя

- **Каналы:** прежний `devices[]`, постоянный ID, тип, функциональная комната, наличие; `bindings[id]` содержит entity_id и отметку проверки. Существующие команды, камера и мастер-выключение продолжают использовать эти IDs.
- **Логические устройства:** `deviceModel.groups[]` объединяет несколько каналов одного прибора. Например, температура, влажность и батарейка становятся одним датчиком. Канал может принадлежать только одному явному устройству; несгруппированный канал автоматически получает отдельное представление без записи в конфигурацию.
- **Представление:** имя, основная комната и `visual.mode` (`room` / `none`) не определяют права на управление. Связь с будущим планом сохраняется отдельно. Новая карточка не требует координат, значка или перерисовки сцены.

Формат дополнения:

```json
{
  "version": 3,
  "deviceModel": {
    "version": 1,
    "groups": [{
      "id": "unit-climate-living",
      "name": "Датчик климата · гостиная",
      "room": "living",
      "members": ["temperature:living", "humidity:living", "battery:living"],
      "visual": {"mode": "room"}
    }]
  }
}
```

Здесь показан фрагмент настроек, не самостоятельный файл для импорта.
`devices`, `bindings` и остальные существующие поля сохраняются.

## Что уже работает

- Технический раздел → **Устройства**: создать группу, изменить имя/основную комнату/состав, разгруппировать без удаления каналов и привязок.
- Технический раздел → **Каталог**: добавить канал поддержанного типа. Он сразу представлен отдельным логическим устройством; членство в группе необязательно.
- **Обзор → Датчики дома**: связанные показания и заряд показываются в одной карточке устройства. Общая сводка батареек сохранена.
- Дополнительные типы **Шторы / карниз** и **Робот-пылесос** можно добавить и привязать для наблюдения. Их карточки появляются в комнате и обзоре; положение/заряд показываются только при наличии числовых атрибутов.
- `GET /api/panel/device-model`: нормализованная структура с компонентами, ролями и категориями. Это конфигурация, не запрос к HA; `availability: unobserved` не означает отсутствие связи. Живое состояние клиент собирает отдельно из проверенных привязок.

Новые устройства сами не импортируются из HA. Поиск кандидатов, выбор источника при
дублях, обобщённые управляющие карточки и редактор плана относятся к следующим этапам.
Сейчас нет команд карнизу/пылесосу, карты уборки, новых маркеров и анимации штор.
Текущая 3D-сцена не читает `visual.mode`; это подготовленные метаданные для её замены.

## Безопасность

Реестр типов вынесен в `src/device-types.js` и используется обеими сторонами.
Он описывает категории и возможные функции; фактические возможности вычисляются
по доступному состоянию. Разрешение команды по-прежнему проверяет серверный адаптер,
а не группа, импортированный JSON или название устройства.

Инженерное оборудование и новые наблюдаемые категории не получают команд через
группировку. Новая линия не включается в мастер-выключение автоматически сервером:
это отдельная настройка существующего каталога. Импорт переводит панель в деморежим
и снимает все отметки проверки, как прежде.

Для нового класса требуется один модуль/адаптер, а не правка каждого экземпляра.
Нестандартные возможности конкретной интеграции могут потребовать отдельного адаптера.
Произвольные сервисы, скрипты и адреса из пользовательских настроек не исполняются.

## Миграция и сохранение

Формат настроек остаётся v3 с добавочной версией модели v1. Старые копии v3 принимаются.
При первом чтении прежнего профиля создаются только известные группы датчиков
дома, двери, мастер-кнопки, камеры и движения террасы, если каналы присутствуют
и относятся к одной зоне. По похожим названиям произвольные приборы не объединяются.
Пользовательские имена каналов, entity_id, подтверждения, тема, фото и режим сохраняются.

Исходный JSON сохраняется один раз в той же SQLite-базе, в таблице `profile_backups`
с ключом `(profile_id, 'before-device-model-v1')`. Запись резервной копии и нового
профиля выполняется одной транзакцией. Это страховочная копия конфигурации, не
отдельный бэкап приложения; перед обновлением по-прежнему сделай резервную копию HA.
Не удаляй приложение ради обновления.

Пустой список групп означает осознанное разгруппирование и не заполняется повторно.
Старые уже открытые клиенты, не знающие `deviceModel`, при сохранении темы не стирают
новую структуру. Неизвестные версии модели и битые ссылки отклоняются без изменения
профиля. При удалении канала через интерфейс его ссылка явно удаляется из групп.

Для разработчика: номера `unit-*` относятся к логическим устройствам; старые IDs
каналов остаются ключами команд. Идентификаторы сущностей HA не являются
идентификаторами логического устройства. Переименование entity_id в HA всё ещё
потребует исправить привязку; автоматического registry-based reconciliation пока нет.

## Проверки и ограничения

Автотесты покрывают миграцию реальной SQLite, сохранение фото/режима/привязок,
повторный запуск, старый клиент, CRUD групп, импорт, неизвестные версии и запрет
эскалации команд. Существующие тесты света, станции, камеры/WebRTC и безопасности
запускаются вместе с новыми. Физический карниз и пылесос не подключались.
